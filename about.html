✦ The Problem

Why LeaveEase Exists

Traditional leave management in organizations is manual, error-prone, and slow. HR teams drown in email chains, spreadsheets, and paperwork. LeaveEase was built to solve this.

📬

No More Email Chains

Traditional leave requests go through long email threads. LeaveEase provides a centralized digital portal where employees apply and HR approves instantly — no back-and-forth emails.

📊

Real-Time Balance Tracking

Employees and HR managers needed live visibility into leave balances, used days, and remaining quota per category. LeaveEase provides this at a glance on every dashboard.

🤖

AI-Assisted Classification

HR manually categorizing each leave request is tedious. LeaveEase uses Gemini AI to automatically suggest the correct leave type based on the employee's reason text — saving time and reducing misclassifications.

🗂️

Persistent & Auditable Data

Leave decisions must be recorded for compliance, payroll, and policy enforcement. LeaveEase uses SQLite to persist all employees, requests, and decisions with full history and HR audit trails.

🎓

Academic Purpose

Built as a 3rd-Year B.Sc. Computer Science Mini Project at a college, LeaveEase demonstrates full-stack development, database design, REST APIs, React UI design, and AI integration in a single cohesive system.

🔄

Role-Based Access Control

Different users need different views. Employees should only see their own data. HR admins need organization-wide visibility. LeaveEase enforces clean role-based access for both persona types.

🔄 Step-by-Step

Application Workflow

From employee login to leave approval — the complete end-to-end journey through LeaveEase.

🔐
Step 01 — Authentication

Employee / HR Login

Users access the portal via email + password login. The system validates credentials against stored employee data and establishes a session. Role detection (Employee vs. HR Admin) happens at this stage, routing the user to their role-specific dashboard.

📋
Step 02 — Leave Application

Employee Applies for Leave

The employee navigates to "Apply for Leave", selects the leave type (Casual, Sick, Earned, Emergency, Maternity/Paternity), specifies dates, duration type (Full Day / Half Day), and enters a reason. The system checks against available balance before submission.

🤖
Step 03 — AI Classification

Gemini AI Analyzes the Request

The employee's reason text is sent to the Gemini API. The AI suggests the most appropriate leave category based on the reason (e.g., "fever and body ache" → Sick Leave). The AI's suggestion is shown as a smart recommendation badge but the employee can override it.

⏳
Step 04 — Pending Queue

Request Enters HR's Review Queue

Submitted requests immediately appear in the HR Admin's "Review Requests" queue with a "Pending" status. The HR Dashboard's KPI card shows the pending count as a live badge. Email notifications (mocked) are triggered to the employee confirming submission.

✅
Step 05 — HR Decision

HR Approves or Rejects

The HR Admin reviews the request details, AI suggestion, reason, and dates. They can approve (with an optional remark) or reject (with a mandatory reason). On approval, the employee's leave balance is automatically deducted. On rejection, the reason is recorded for the employee to see.

📊
Step 06 — Reporting & Analytics

Data is Logged, Reported, and Audited

All decisions are persisted in SQLite. HR can view the full Leave History, department-wise analytics, monthly leave volume trends, leave-type breakdowns, and an audit trail of all HR actions. Employees can view their own request history with HR remarks.

🗄️ Data Layer

SQLite Database Schema

All application data is stored in leave_ease.db — a local SQLite file with 4 core tables. Browse it live at localhost:4000 →

employees

id TEXT PK
employee_code TEXT
name TEXT
email TEXT UNIQUE
phone TEXT
department TEXT
designation TEXT
role TEXT
joining_date TEXT
password TEXT

leave_balances

id INTEGER PK
employee_id FK → employees
casual_total INTEGER
casual_used REAL
sick_total INTEGER
sick_used REAL
earned_total INTEGER
earned_used REAL
emergency_total INTEGER
emergency_used REAL

leave_requests

id TEXT PK
employee_id FK
leave_type TEXT
start_date TEXT
end_date TEXT
days_count REAL
duration_type TEXT
reason TEXT
status TEXT
hr_remarks TEXT
ai_suggested INTEGER

Relationships

employees ↔ leave_balances
One employee → one balance record per year
employees → leave_requests
One employee → many requests (history)
Cascading DELETEs and FK constraints enforce referential integrity
